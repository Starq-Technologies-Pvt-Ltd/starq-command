
Starq Command: Canonical Control-Plane Architecture and Build Doctrine
1. Executive Purpose and System Boundaries
Starq Command functions as the internal operating control plane for Starq’s engineering organization. It is designed to enable a single human Founder to supervise, coordinate, and govern a heterogeneous fleet of artificial intelligence engineering seats operating across multiple commercial products, foundation model providers, local host runtimes, source code repositories, and independent verification stages. Command does not replace existing lower-level development utilities, local integrated development environments (IDEs), distributed version control systems (Git), continuous integration and continuous deployment (CI/CD) pipelines, active runtime brokers (Herdr), or project-specific Single Sources of Truth (SSOTs). Instead, Command operates strictly above these components as an authoritative governance cockpit.
The primary objective of this architecture package is to formalize and upgrade the existing Command and Herdr implementation into a durable v1 control plane, execute rigorous independent acceptance testing, and immediately place the codebase into a maintenance-only freeze. This lifecycle boundary ensures engineering bandwidth returns entirely to core commercial product delivery across StarqERP, Starq POS, Hoadha, and the broader commercial application ecosystem.
1.1 Historical Context and System Separation
The operational posture of Starq Command is rooted in two foundational realities:
First, Starq operated a heterogeneous, multi-provider agent fleet prior to the introduction of Herdr. The organizational model already incorporated named organizational seats (such as Elder, Vision, Codex, Antigravity, Cursor, Deadpool, Pi, OpenCode, and Goose), distinct underlying vendor APIs, manual task distribution, Founder-directed routing, Room-based coordination, persistent project SSOT specifications, builder-verifier organizational separation, and quota-aware seat allocation. Herdr did not introduce the concept of the fleet. Rather, Herdr was engineered to resolve missing low-level operational capabilities: host process lifecycle visibility, deterministic session ownership, bounded process execution boundaries, launch eligibility enforcement, operating system process identity tracking, and pseudo-terminal (PTY) supervision.
Second, Starq Command existed as a management interface prior to native Herdr integration. Command was initially conceived as the strategic cockpit, whereas Herdr emerged as the local execution floor. Consequently, their integration must preserve strict architectural separation rather than collapsing into a monolithic daemon.

2. Starq Management Model and Entity Taxonomy
The governance of Starq’s engineering fleet requires clear structural boundaries between organizational authority, persistent responsibilities, commercial vendors, transient execution runtimes, and units of work. The operational hierarchy cascades through eight formal tiers:
Founder: The root human authority within Starq's lawful corporate governance, holding non-delegable control over capital, production deployment, and constitutional rules.
Command (Control Plane): The centralized orchestration engine that translates Founder intent into statefully tracked tasks, enforcing leases and verification gates.
Seat: A persistent functional responsibility assigned to a specific domain (such as core building, verification, or security auditing).
Provider / Model: The foundational external intelligence infrastructure and reasoning engines contracted to execute analytical work.
Harness: The client binary or CLI tool facilitating local filesystem and tool interaction.
Session: The ephemeral runtime environment managed on the execution floor by Herdr.
Task: The atomic, verifiable unit of engineering work defined by a machine-readable contract.
Subagents: Tactical child processes spawned within a harness session for temporary, parallelized sub-tasks.
2.1 Entity Taxonomies and Operational Definitions
The operating model enforces precise boundaries between organizational identity and execution mechanisms:
Founder: The final human operating authority within Starq’s corporate structure. The Founder retains non-delegable authority over capital allocation, production deployments, cryptographic root keys, strategic SSOT modifications, architectural freeze overrides, and binding dispute resolutions between seats.
Seat: A persistent organizational role holding continuous domain responsibilities within Starq. Named seats represent functional posts (for instance, Antigravity as Primary Core Builder, Vision as Independent Verification Authority, Elder as Strategic Architectural Counsel). A seat persists indefinitely across shifts, software upgrades, model migrations, and provider outages. A seat is explicitly distinct from the underlying foundation model powering it.
Provider: A commercial or open-source infrastructure entity supplying foundation model access (such as Anthropic, OpenAI, Google, or local inference runtimes). Providers are external vendors subject to transient latency, rate-limiting, terms of service revisions, and infrastructure outages.
Model: A specific versioned reasoning engine hosted by a provider (for example, claude-3-5-sonnet-20241022 or gpt-4o-2024-08-06). Models are swappable analytical engines assigned to seats based on operational requirements.
Harness: The client binary, CLI tool, or interactive environment through which a model accesses local tools and file systems (including Claude Code, Codex CLI, Antigravity CLI, Cursor, and OpenCode). The harness enforces local protocol boundaries, manages user prompt contexts, and interfaces directly with the terminal or PTY floor1.
Session: A transient, bounded runtime execution context initialized within a harness to perform work. A session begins at process invocation, accumulates conversational and token context, and terminates upon task completion, fatal failure, or explicit suspension. Sessions are ephemeral and do not outlive host restarts.
Subagent: A temporary, tactical child process or specialized reasoning thread spawned dynamically inside a provider harness. Subagents lack persistent organizational identity, cannot own durable tasks, and report strictly to their parent seat session.
Task: An atomic, statefully tracked unit of engineering work defined by a machine-readable Task Contract. A task possesses a permanent identifier, clear file boundary constraints, an allocated builder seat, an assigned verifier seat, and deterministic acceptance criteria.
Artifact: A machine-readable, cryptographically verified record produced upon task completion. Artifacts capture the precise baseline Git commit SHA, candidate commit SHA, modified files, diff statistics, executed commands, test outputs, exit codes, and operational telemetry.
Verification: An independent, adversarial technical evaluation of a candidate SHA executed by an authorized verifier seat in a clean workspace, validating strict adherence to the Task Contract without reliance on builder claims.
3. Multi-Provider Fleet Doctrine
Starq explicitly rejects architectural lock-in to any single artificial intelligence vendor. The engineering fleet is deliberately designed to operate across multiple competing foundation model providers simultaneously.
3.1 Strategic Rationale for Provider Diversity
Operating across distinct provider platforms mitigates several single-vendor failure modes:
Quota Resilience: Provider-specific hourly, daily, or weekly rate limits cannot halt Starq’s overall engineering throughput. Exhaustion of one provider's token allocation triggers deliberate task redirection to seats backed by alternate infrastructure.
Capability Diversity: Foundation models exhibit divergent proficiencies. Certain architectures excel at large-scale refactoring and deep code synthesis, others at rigorous formal logic, semantic auditing, or fast tool-calling loops. Maintaining a diverse fleet aligns task requirements with model advantages.
Outage Protection: Complete cloud service disruptions, regional networking degradations, or vendor service-level agreement (SLA) failures at one provider do not halt ongoing product development.
Verification Independence: An architectural defect or systematic reasoning blind spot within a given model family will frequently recur if that same model family is tasked with verifying its own output. Employing a structurally distinct model family for verification provides meaningful adversarial rigor.
Vendor Independence: Maintaining dynamic interoperability prevents architectural capture by any single artificial intelligence laboratory.
3.2 Stable Assignment Versus Automated Per-Token Hopping
Starq distinguishes between deliberate fleet diversity and automated, dynamic model hopping:
Automated, runtime model hopping—wherein individual prompt completions, conversational turns, or sub-steps within an active code-mutation task are routed across disparate providers via probabilistic middleware—is prohibited. Dynamic routing obscures context history, breaks prompt-cache efficiency, creates non-deterministic debugging traces, complicates intellectual property provenance, and destroys local environment consistency.
Starq operates on a model of stable seat assignment coupled with deliberate, explicit fallback reassignments. A seat is assigned a designated provider, model, and harness for sustained durations. When a task is dispatched to a seat, that seat retains operational ownership across the builder lifecycle.
If a quota exhaustion event, prolonged outage, or capability failure necessitates reassigning a task to a different seat operating on an alternate provider, this transition must occur cleanly at a task boundary. The transition requires the emission of a typed reassignment event to Room, the release and re-granting of workspace locks, and the capture of all intermediate progress within an explicit Git commit. Undocumented runtime provider failover during an uncommitted file mutation cycle is forbidden.
4. Tactical Subagent Governance and Execution Doctrine
Modern agent harnesses frequently provide capabilities to spawn autonomous subagents. Starq Command strictly governs the invocation, operational scope, and execution boundaries of these ephemeral child processes.
4.1 Tactical Acceleration Versus Organizational Delegation
Subagents represent tactical accelerators rather than organizational entities. They are transient execution mechanisms invoked by an authorized seat to handle isolated workloads. They hold no organizational rank, cannot accept tasks directly from Command, cannot verify tasks for final acceptance, and cannot interact directly with Room outside the supervision of their parent seat.
Hierarchically, the parent seat session initiates the subagent, defines its bounded scope, collects the subagent's return output, verifies the tactical contribution, and retains exclusive responsibility for committing modifications to the repository worktree.
4.2 Explicit Criteria for Subagent Invocation
A seat may spawn subagents only when a task satisfies one or more of the following operational conditions:
The task requires parallel exploration or analysis across independent directories, documentation sets, or external specifications that would saturate the primary context window.
The task involves isolated analytical inspection, such as static security scanning, style conformance auditing, or dependency graph generation, where context isolation prevents prompt contamination.
The task requires an adversarial cross-examination of a proposed implementation strategy prior to writing file mutations to disk.
The task modifies isolated, non-overlapping components where parallel scratch directories can be managed safely under parent process supervision.
Subagents are prohibited under any of the following operational constraints:
The task is small, cohesive, or touches fewer than three contiguous files.
The workspace environment cannot provide isolated directory boundaries, introducing race conditions on shared files.
The parent seat is operating under restricted provider API quotas, where the multiplicative token consumption of parallel execution risks immediate quota exhaustion.
The task coordination overhead (prompt construction, output parsing, schema reconciliation) exceeds the direct implementation effort.
The provenance of generated code would become obscured by unlogged subagent generations.
4.3 Provenance and Execution Constraints
All subagent operations must execute within the file boundary constraints established by the parent task’s contract. Subagents must never spawn secondary unmonitored background daemons that survive the parent session.
When a parent seat completes a task that utilized subagents, the resulting Builder Completion Artifact must record the total subagent count, the tactical scope assigned to each child, their cumulative token and context consumption, and an explicit verification that all child processes terminated prior to candidate SHA generation.
5. Canonical Vision of Starq Command
Starq Command is the Founder-facing operational control plane for Starq’s digital engineering organization. It serves as an authoritative cockpit, providing continuous, high-fidelity visibility and deterministic control over all engineering activities executed across the company's autonomous fleet.
Command makes the engineering organization legible. It eliminates operational opacity by aggregating distributed, multi-repository, multi-provider, and multi-machine activities into a unified, coherent operating model. From a single interface, the Founder can instantly assess:
The exact set of active commercial and internal software products currently under construction or maintenance.
Every registered, active, blocked, or queued engineering task across the enterprise.
The specific seat assigned to each task, along with its active provider, foundation model, CLI harness, and host execution environment.
Real-time quota capacity, remaining rolling-window token balances, rate-limit proximity, and projected reset horizons across all integrated model providers.
The exact host workspace, Git branch, and isolated worktree allocated to every executing task.
The real-time status of code mutations, including active diff statistics, files touched, test execution progress, and exit codes.
Machine-readable proof artifacts generated upon task completion, including baseline commit SHAs, candidate commit SHAs, and reproduction logs.
The independent verification status of every completed task, identifying the assigned verifier seat, the clean verification environment used, tests executed, and formal verdicts rendered.
Operational bottlenecks, stuck execution loops, stale workspace leases, and unhandled runtime exceptions.
System events requiring explicit Founder intervention, balanced against routine automated transitions that require no manual oversight.
Command does not compete with project repositories, Git workflows, or runtime terminal supervisors. It binds these elements into an auditable control structure, ensuring that engineering velocity is matched with rigorous verification, strict security boundaries, and total corporate governance.
6. Target v1 Architecture and Service Boundaries
The v1 architecture of Starq Command establishes strict separation between strategic governance, durable persistence, execution monitoring, and local host runtimes.
The control plane hierarchy routes downward from the Founder Cockpit through the Starq Command Server, which hosts the core sub-services: Task Controller, Routing Engine, Evidence and Verification Service, Capacity Monitor, Stuck Detector, and Worktree Lease Manager. These services interface downward with four persistent adapters: the Relational Task Store, the Hash-Addressed Artifact Store, the Room Event Adapter, and the Herdr Transport Client. The transport client bridges across an authenticated loopback connection to Herdr on the execution floor, which directly supervises the host processes, PTY allocations, and provider harnesses.
6.1 Architectural Subsystem Specifications
The subsystem boundaries and operational constraints are defined as follows:
Task Control Plane: Holds durable task state machines, validates state transitions, manages task dependencies, and enforces lease expirations. The Task Control Plane is the sole system component authorized to alter a task's state.
Workspace and Lease Manager: Governs Git worktree allocations, validates branch naming conventions, manages exclusive filesystem locks, monitors lease heartbeats, and handles the recovery of abandoned workspaces.
Evidence and Verification Engine: Ingests, validates, and archives Builder Completion Artifacts and Verifier Artifacts. Guarantees that verifiers evaluate exact candidate commit SHAs within fresh, isolated worktrees.
Stuck and Failure Detector: Evaluates operational telemetry emitted by Herdr and provider harnesses against configurable heuristics to detect process hangs, command repetition loops, runaway resource consumption, and unhandled errors.
Capacity and Quota Service: Tracks real-time token consumption, rolling-window rate limits, and provider account status to inform decision-support routing and prevent fleet-wide quota exhaustion.
Herdr Transport Layer: An abstracted communication interface decoupling Command from Herdr's local communication mechanism. In v1, this operates over authenticated loopback HTTP/JSON-RPC; its interface preserves future adaptability for remote worker daemons without requiring changes to Command's core business logic.
Room Adapter: Ingests and publishes structured event envelopes to Room’s append-only operational log, maintaining bidirectional synchronization between Command's database and the human-readable ledger.

7. Durable Task Control Plane and State Machine
The v1 Task Control Plane replaces ad-hoc status tracking with a strictly validated, durable finite state machine. Tasks progress through a deterministic lifecycle, preventing race conditions, dual assignments, and unverified merges.
7.1 Canonical Task Lifecycle State Machine
A task must transition through formal operational stages:
Creation & Queuing: A task originates in CREATED upon validation of its Task Contract, moving to QUEUED once dependency checks pass.
Allocation & Execution: The task transitions to ALLOCATED when assigned to an eligible seat, and enters EXECUTING once an isolated Git worktree is provisioned and a lock lease acquired.
Intermediate Interrupts: During execution, the task may transition to BLOCKED (re-entering EXECUTING upon unblocking), FAILED (due to terminal process crashes), or CANCELLED (via Founder directive).
Builder Finalization: When implementation ends, the seat emits a verified candidate SHA and Builder Completion Artifact, transitioning the task to BUILDER_COMPLETE.
Verification Phase: Command immediately transitions the task to VERIFYING, allocating an independent verifier seat in a detached, clean worktree.
Resolution: The verifier issues a formal verdict. A PASS transitions the task to ACCEPTED (authorizing trunk merge). A FAIL transitions the task to REJECTED, routing it back to ALLOCATED or EXECUTING for corrective iteration.

7.3 Task Storage and Relational Schema
For the v1 implementation, task state is persisted using an embedded SQLite database configured in Write-Ahead Logging (WAL) mode (PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA foreign_keys=ON;). SQLite provides atomic transactions, high read concurrency, and operational durability without introducing external network service dependencies.

8. Workspace Isolation and Git Worktree Specification
To maintain code integrity and support concurrent development, Starq enforces a strict filesystem isolation rule:
Every concurrent code-mutating task requires an isolated, dedicated Git worktree.
Shared checkouts, concurrent operations within a single working directory, and mutations directly on primary branches are strictly prohibited. Read-only inspections may target shared reference checkouts, but any task modifying code must operate within an isolated worktree.
The repository filesystem architecture enforces separation between primary storage and active worktrees:
Primary Git Repository: Located at /srv/repos/<project>/.git/
Builder Workspace: Provisioned at /srv/repos/<project>/.worktrees/<task-id>-<slug>/, checked out on branch task/<task-id>-<slug>, holding an exclusive .worktree-lease file.
Verifier Workspace: Provisioned at /srv/repos/<project>/.worktrees/verify-<task-id>-<slug>/, checked out in clean DETACHED HEAD state targeting the exact candidate SHA.
8.1 Worktree Provisioning and Branch Naming
Worktrees must be provisioned systematically according to deterministic conventions:
Filesystem Location: All task worktrees reside within a designated directory inside or alongside the repository root: .worktrees/<task-id>-<sanitized-slug>.
Branch Conventions: Branches created for code-mutating tasks follow the pattern: task/<task-id>-<sanitized-slug>. Long-lived seat branches are prohibited.
Base Commit Pinning: When a worktree is created, it branches from a verified base SHA specified in the Task Contract. The creation command executes as:git worktree add -b task/<task-id>-<slug> .worktrees/<task-id>-<slug> <base-sha>
Verification Worktree Isolation: When a task reaches BUILDER_COMPLETE, the verifier does not inspect the builder's active worktree. The verifier provisions a distinct, clean worktree detached at the candidate SHA:git worktree add --detach .worktrees/verify-<task-id>-<slug> <candidate-sha> This ensures that uncommitted artifacts, untracked intermediate files, or environment configurations from the builder cannot alter verification results.
8.2 Lock Leases, Heartbeating, and Stale Detection
Worktree access is guarded by mutual-exclusion leases managed by Command:
Lease Acquisition: Upon transitioning to EXECUTING, the seat acquires a time-bounded lease. Command writes a .worktree-lease metadata file at the root of the worktree, containing the task ID, owning seat ID, lease token, and expiration timestamp.
Lease Duration and Heartbeating: Default leases are granted for 3,600 seconds (1 hour), with an allowable maximum of 14,400 seconds (4 hours). The seat or its monitoring harness must emit a heartbeat to Command at least once every 300 seconds. Command extends the lease upon receiving valid heartbeats.
Stale Lease Detection: If a lease expires without a heartbeat, Command flags the task as SUSPECTED_STUCK. Command does not immediately purge the directory. It queries Herdr to determine whether the registered OS process group is active. If Herdr confirms the process has terminated, Command revokes the lease.
8.3 Non-Destructive Workspace Recovery and Cleanup
Under no circumstances may automated processes execute destructive Git operations—such as git reset --hard, git clean -fdx, or recursive directory deletions—against an uncommitted or recovering workspace.
Abandoned Workspaces: If a builder crashes or is terminated, Command marks the workspace as abandoned.
Preservation Stash: Before removing an abandoned worktree, Command instructs Herdr to capture any untracked or uncommitted changes onto an orphan recovery branch:git --work-tree=<path> add -A && git --work-tree=<path> commit -m "recovery: auto-stash abandoned state for <task-id>"
Pruning: Only after untracked work is preserved into Git object storage does Command unmount and delete the worktree via git worktree remove --force <path>.
Post-Acceptance Pruning: Once a task transitions to ACCEPTED and its branch is merged into the integration trunk, Command removes the builder and verifier worktrees, deletes the local task branch, and runs git worktree prune.

11. Verifier Contract, Artifact, and Verdict Specification
The verification stage provides an adversarial barrier between code construction and trunk integration. A verifier seat never trusts builder narratives, execution logs, or local workspaces. It independently checks out the candidate commit SHA in an isolated verification worktree, executes mandated test commands, audits boundary conditions, and returns a formal verdict.
The operational flow enforces an audit checkpoint: the verifier audits the candidate SHA in an isolated worktree. If the audit yields PASS, merge authority is granted and the task enters ACCEPTED. If the audit yields FAIL, the candidate SHA is blocked from trunk, the task transitions to REJECTED, and the findings are routed back to the builder seat for remediation.

11.2 Verifier Verdict Definitions and Authority Actions
The verifier must render one of three valid verdicts:
PASS: The candidate SHA satisfies all acceptance criteria in the Task Contract. Independent execution of required test suites passed with exit code 0. Boundary audits confirm zero out-of-bounds file mutations or prohibited command executions. Code coverage meets or exceeds configured minimums. The Task Control Plane automatically authorizes trunk merge and transitions the task to ACCEPTED.
FAIL: The candidate SHA fails to satisfy acceptance criteria, triggers test failures, violates boundary path rules, introduces regressions, or exhibits syntax/type errors. The task is transitioned to REJECTED, and the verifier's findings are appended to the task ledger. The workspace lock is returned to the builder for corrective action.
CONDITIONAL: Core functionality and tests pass, but minor non-breaking discrepancies or documentation gaps are identified. A CONDITIONAL verdict does not permit automatic merge. The task transitions to BLOCKED, requiring Founder review to accept the condition or instruct a corrective builder pass.

13. Stuck and Execution Failure Detection Subsystem
Autonomous execution runtimes can encounter unhandled failure modes: deadlocks, infinite tool loops, repeated compilation failures, process hangs, and context saturation. Starq Command implements an active, stateful stuck detector.
13.1 Stuck Detection State Lifecycle
The stuck detection lifecycle operates through progressive operational stages:
RUNNING: Normal execution where process heartbeats, CPU cycles, and tool interactions occur within expected parameters.
SUSPECTED_STUCK: Initial detection when heuristic thresholds are exceeded (for instance, identical error repetitions or filesystem inactivity).
STUCK: Confirmed hung state after repeated heuristic failures without intervening task progress.
PAUSED: Automated platform-appropriate process suspension executed via Herdr, holding process memory intact.
Resolution paths from PAUSED: The process may be RESUMED following Founder review, ESCALATED to reassign intermediate progress to an alternate seat, or TERMINATED to release resources and fail the task cleanly.
13.2 Detection Signals and Heuristic Indicators
The stuck detector continuously evaluates execution telemetry streams against configurable thresholds:
Command Repetition Loop: The seat executes the identical shell or tool command three or more consecutive times with identical parameters and receives identical non-zero exit codes.
Error Invariance: Compiling or testing produces identical error output across successive turns without modifying intervening source code.
Filesystem Inactivity: A code-mutating task in the EXECUTING state produces zero file write operations, Git index modifications, or directory timestamp updates for longer than 900 seconds (15 minutes).
Terminal Stream Cessation: An active PTY process allocated by Herdr emits zero bytes to stdout/stderr over a configurable observation window (default: 600 seconds), while consuming either 0% or 100% host CPU.
Tool-Call Thrashing: The session generates continuous API tool-call requests without producing code changes, progressing the task state, or terminating the conversational turn.
Token Burn Runaway: Cumulative token consumption for a single task exceeds 250% of the historical median for that task type without generating a candidate commit SHA.
13.3 Process Suspension and Escalation Protocol
The detection subsystem prioritizes non-destructive intervention:
Pause Before Kill: When an execution process hangs, Command pauses the process rather than terminating it, preserving memory state and diagnostic traces for inspection.
When a task transitions from SUSPECTED_STUCK to STUCK, Command issues a platform-appropriate process suspension request to Herdr:
On Linux and macOS hosts, Herdr dispatches SIGSTOP to the target process group, halting CPU cycles while preserving RAM state, open file handles, and PTY buffers.
On Windows hosts, Herdr suspends all threads within the target process hierarchy via platform-appropriate system calls.
Command records the state as PAUSED, generates an operational event to Room, and alerts the Founder cockpit.
From the cockpit, the Founder or an authorized operator can inspect the session diff, examine the terminal buffer, and select one of three actions:
Resume: Issues platform-appropriate process resumption (such as SIGCONT) to allow the process to continue.
Escalate: Detaches the workspace, preserves intermediate files to a recovery branch, terminates the session, and reallocates the task to an alternate seat.
Terminate: Issues termination signals, revokes the workspace lease, marks the task as FAILED, and releases runtime resources.
14. Quota and Fleet Capacity Management
Dynamic multi-provider fleet operations require real-time capacity tracking to prevent sudden throughput drops caused by provider rate-limiting.
14.1 Capacity Accounting Model
Starq Command tracks capacity across four distinct dimensions:
Rolling Window Consumption: Tracking tokens consumed across 1-minute, 1-hour, and 24-hour sliding windows against vendor-enforced Requests-Per-Minute (RPM) and Tokens-Per-Minute (TPM) limits.
Periodic Account Quotas: Tracking cumulative spending against fixed weekly and monthly account expenditure ceilings.
Active Context Saturation: Monitoring the token size of active conversations within each seat harness relative to model context windows.
Reset Horizons: Projecting the time remaining until rate-limit counters reset, enabling intelligent task scheduling.
14.2 Implementation Status Discipline
To prevent future planned capabilities from being mistaken for active production features, Command enforces an architectural status discipline. Every component and feature must carry exactly one unambiguous status:
IMPLEMENTED: Actively executing in production code with operational tests.
PARTIAL: Partially functional; underlying hooks exist but user-facing interfaces or edge-case handling remain incomplete.
REQUIRED BEFORE FREEZE: Mandatory capability that must be built, verified, and accepted prior to initiating the maintenance freeze.
PLANNED: Architecturally specified for post-v1 evolution; no production code written.
FUTURE: Conceptual extension point reserved for long-term scalability.
DEFERRED: Evaluated and intentionally postponed.
PROHIBITED: Explicitly disallowed by corporate architecture doctrine.
UNRESOLVED: Open architectural question requiring Founder determination.

17. Command User Interface Information Architecture
The Command interface is designed as an operational flight cockpit for the Founder. The layout provides immediate clarity across all levels of the organization, prioritizing system state and actionable exceptions over decorative visual elements.
The UI layout is divided into four synchronized operational viewports:
Viewport 1 (Critical Gates): Displays pending approvals, blocked tasks, and active stuck alerts requiring immediate Founder intervention.
Viewport 2 (Fleet Status Matrix): Real-time matrix of seats, current task bindings, provider status, and context saturation levels.
Viewport 3 (Lifecycle Pipeline): Visual swimlane of tasks across Queued, Executing, Builder Complete, and Verifying states.
Viewport 4 (Operational Stream): Live chronological log of Room events, builder submittals, and verifier verdicts.
17.1 Screen-by-Screen Information Specifications
The interface is structured into seven primary functional views:
Overview Cockpit: The executive operational dashboard. Displays active projects, real-time throughput metrics, blocked tasks requiring resolution, gates awaiting Founder sign-off, provider quota status gauges, and critical alerts.
Fleet Matrix: Real-time operational status of all registered seats. Displays active providers, assigned models, current task bindings, CPU and memory utilization, context window saturation gauges, active lease durations, and runtime health indicators.
Task Control Board: Lifecycle management view organized by state (QUEUED, ALLOCATED, EXECUTING, BLOCKED, BUILDER_COMPLETE, VERIFYING, ACCEPTED, REJECTED). Allows filtering by project, risk class, and assigned seat.
Evidence and Verification Vault: Audit repository for Builder Completion Artifacts and Verifier Artifacts. Provides diff views, test logs, coverage reports, SHA provenance trees, and side-by-side builder/verifier comparisons.
Herdr Floor Monitor: Direct operational interface with the Herdr runtime broker. Displays active host processes, OS process group trees, PTY terminals, session lease files, loopback connection status, and bounded command interfaces.
Room Stream: Live, structured operational ledger stream combining human-readable messages with typed system events. Supports sequence filtering, thread tracking, and event payload inspection.
Alerts and Incident Console: Dedicated view for operational exceptions: stuck agent loops, process hangs, dirty worktree flags, stale lease expirations, verification rejections, and provider rate-limit alerts.

19. Room Compaction and Provenance Retention Architecture
As long-running operations accumulate thousands of conversational turns and lifecycle records, ledger files can exceed practical context window limits for active agent sessions. Room handles this with a compaction strategy that preserves complete operational provenance.
The historical storage architecture maintains a strict dual-tier model:
Primary Tier: Raw append-only historical log (room-events.jsonl), which is never truncated, modified, or overwritten.
Secondary Tier: Periodic snapshot files generated every 1,000 sequence events (e.g., snap-seq-001000-002000.json), storing cryptographically validated state summaries.
Injection Engine: When new sessions initialize, the engine injects the project SSOT, the latest compacted snapshot, and the uncompacted event tail, avoiding token saturation while preserving full context continuity.
The compaction engine separates raw historical records from derived query representations:
Raw Immutable Log: The primary journal (room-events.jsonl) is strictly append-only. Raw records are never deleted, overwritten, or modified. This journal serves as the definitive audit ledger.
Sequence-Bounded Snapshots: A background compactor runs at periodic sequence intervals (for example, every 1,000 events) to produce a structured snapshot. Snapshots contain:
The exact inclusive sequence number range (start_sequence, end_sequence).
Current task statuses, including all ACCEPTED and active tasks.
A cryptographic SHA-256 hash covering the sequence of compacted raw records.
An indexed summary of major engineering decisions and Founder rulings.
Context Injection Optimization: When a seat session initializes and requests Room context, Command does not supply the full raw history. The injection engine compiles an optimized context payload containing:
The project's durable SSOT architectural specification.
The most recent compacted state snapshot.
The uncompacted event tail (events occurring after the snapshot's end_sequence).
Audit Verification: If an audit or debugging trace requires historical analysis, Command can replay the entire raw journal from sequence 1 to verify any intermediate snapshot.

21. Fail-Closed Security Model and Boundary Invariants
Herdr and Command implement a fail-closed security perimeter. They enforce strict access boundaries to ensure that automated agents, browser interfaces, and network services operate within least-privilege constraints.
21.1 Core Security Invariants
The security model enforces eight core operational controls:
Loopback Boundary Enforcement: Herdr and Command services bind exclusively to loopback network interfaces (127.0.0.1 and ::1). Binding to public host interfaces (0.0.0.0) is structurally prohibited and rejected at startup.
HTTP Host Header Validation: All incoming HTTP requests to Command and Herdr validate the HTTP Host header against an allowlist containing only localhost and 127.0.0.1:<PORT>. Requests with missing or mismatched Host headers are rejected with HTTP 403.
Origin Header and CORS Whitelisting: The HTTP API checks incoming Origin headers on all mutating endpoints (POST, PUT, DELETE). Cross-origin requests from arbitrary web origins are blocked to prevent Cross-Site Request Forgery (CSRF).
Cryptographic CSRF Tokens and Session Binding: Browser-to-Command operations require a cryptographically random, per-session anti-CSRF token passed in custom request headers (X-Starq-CSRF-Token).
Launch Eligibility Gating: Herdr does not maintain a generic shell execution endpoint. Herdr executes commands exclusively from an authorized allowlist of binaries and CLI harnesses defined in host configuration profiles. Commands attempting to invoke unlisted binaries or raw shell interpreters are rejected.
No Direct Browser-to-Shell Gateway: The Command web UI cannot send arbitrary shell commands directly to the host operating system. The UI communicates strictly through structured task lifecycle requests and bounded administrative endpoints.
Immutable Audit Logging: Every process invocation, suspension, termination, worktree allocation, and task transition is written to an append-only, tamper-evident security audit log on disk.
Fail-Closed Lease Expiration: If Command loses communication with Herdr or crashes, active workspace leases expire automatically. Herdr will not grant new execution requests until secure communication with Command is re-established.

22.2 Context Optimization and Handoff Mechanics
When a seat reaches the COSTLY or EXHAUSTION_RISK thresholds, the system manages the transition through structured protocols:
In-Session Compaction: If supported by the harness, the seat runs a context compaction routine, writing a structured summary of progress and next steps while releasing unneeded file buffers from context.
Clean Session Rotation: If context saturation persists, the seat writes an intermediate Git commit containing all passing changes. Command then terminates the saturated session, launches a fresh session within the same worktree, and injects the baseline Task Contract along with the progress summary.
Seat-to-Seat Handoff: If context limits prevent the assigned builder from completing the task, the task is marked as BLOCKED. Command records intermediate progress, frees the active session, and recommends handoff to an available seat with clean context capacity.
23. Subagent Resource Accounting and Provenance Tracking
When a primary seat spawns tactical subagents, their resource utilization and code modifications must remain attributable to the parent seat. Subagents never operate as untracked background processes.
23.1 Subagent Accounting Requirements
Accounting systems track subagent execution through explicit attribution constraints:
Hierarchical Attribution: Every subagent process is mapped to its parent seat ID, parent session ID, and parent task ID.
Aggregated Resource Tracking: Tokens consumed, wall-clock compute duration, memory allocations, and API charges incurred by subagents are aggregated into the parent task’s accounting ledger.
Filesystem Mutation Restrictions: Subagents are restricted from writing directly to primary worktree branches. Subagents operate in read-only analysis modes or write to dedicated scratch subdirectories (.scratch/subagent-<id>/). The parent seat reviews, stages, and commits all final code changes.
Provenance Verification: The Builder Completion Artifact must record all subagent interactions, detailing their assigned tasks, durations, and outputs to maintain code provenance.
24. Maintenance Freeze Doctrine and Reopening Criteria
Following the completion of Wave 4 and successful independent acceptance verification by Vision, Starq Command enters a strict Maintenance Freeze.
24.1 Rationale and Objectives of the Maintenance Freeze
Command is internal infrastructure designed to support the construction and delivery of Starq’s commercial software portfolio. Continued development on Command beyond v1 operational stability diverts engineering focus from commercial product milestones: StarqERP, Starq POS, Hoadha, and upcoming market launches.
Once Command achieves v1 acceptance, the codebase is placed into maintenance mode. Feature additions, architectural refactorings, and UI enhancements are prohibited until commercial milestones are achieved.
24.2 Explicit Reopening Criteria
The maintenance freeze can be unlocked only under six specific operational conditions:
Verified Production Defect: A reproducible defect within Command or Herdr that compromises task state durability, causes code loss, or corrupts Git workspaces.
Security Vulnerability: A confirmed vulnerability compromising the loopback boundary, host authentication, secret masking, or process isolation.
Provider API Breakage: Upstream vendor changes (such as deprecation of underlying model APIs or breaking modifications to harness CLI protocols) that prevent seats from executing tasks.
Critical Operational Bottleneck: A demonstrated, systemic bottleneck within Command’s control plane that materially degrades product delivery across active product repositories.
Mandatory Integration Requirement: A newly introduced, revenue-critical product requiring novel operational hooks that cannot be accommodated by existing v1 interfaces.
Explicit Founder Executive Ruling: The Founder issues a signed, written directive instructing the engineering fleet to reopen Command for specified upgrades.
External artificial intelligence market announcements, rival developer tooling releases, or cosmetic enhancement proposals do not constitute valid grounds for reopening Command.

Stop Conditions: Antigravity must halt implementation and alert the Founder upon encountering:
Any failure in the core state machine that permits a task to transition directly from EXECUTING to ACCEPTED without verification.
Any unhandled host-level permission issue preventing deterministic creation of isolated Git worktrees.
Any data-loss event within the Room event journal or SQLite state store during simulated crash recovery.
